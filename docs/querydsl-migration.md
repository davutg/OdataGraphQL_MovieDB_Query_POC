# GraphQL Querydsl/JPA migration

## Preserved JDBC version

Branch `archive/jdbc-template`, commit `401fd16`, preserves the JDBC GraphQL implementation and its documentation. The older `RUNNING1` tag remains unchanged. The Querydsl migration continues on `main`.

## What changed

Both APIs now use the same JPA entity relationship mapping and EclipseLink ORM:

```text
OData    → SAP OData JPA Processor → JPA / EclipseLink → guarded JDBC → PostgreSQL
GraphQL  → Spring Data / Querydsl → JPA / EclipseLink → guarded JDBC → PostgreSQL
```

The GraphQL resolver no longer constructs SQL, converts result-set columns into maps, or looks for `nodes/director` to choose a SQL join. GraphQL reads entity getters and handles aliases, fragments, and directives through its execution engine.

| Component | Responsibility |
|---|---|
| `MovieGraphql` | Expose the existing connection query/count field, declare permitted input names, bridge request state. |
| `MovieRepository` | Spring Data repository and declarative Querydsl equality/range bindings. |
| Generated `QMovie` / `QDirector` | Typesafe paths generated from JPA entities during Maven compilation. No hand-maintained SQL column mappings. |
| `QuerydslConnection<T>` | Reusable policy validation, input binding, deterministic ordering, signed pagination and optional count. |
| `QueryRepositoryImpl<T, ID>` | Generic bounded Querydsl JPA window without an automatic count query. |
| `Movie` / `Director` | Common ORM mapping for both protocols. |
| `GuardedDataSource` | Inspect and constrain the SQL generated by either API. |

Spring Data provides the predicate builder, repository lifecycle, transactions, and standard Querydsl count executor. Querydsl builds JPQL, and EclipseLink translates it into PostgreSQL SQL and materializes entities.

## Why a connection adapter remains

This uses Spring Data Querydsl/JPA, rather than Spring GraphQL's stock `QuerydslDataFetcher`. The existing schema has a `nodes` connection, total-budget `first`, optional `totalCount`, signed query-bound cursors, and support for the older Java 8 stack. Stock repository auto-registration does not reproduce that whole contract.

The reusable adapter retains these rules in one place. It does not generate a GraphQL schema or expose every entity automatically. A new entity needs its JPA mapping, generated Q type, schema, repository bindings and a small endpoint registration. Custom business transformations still need resolvers or services. The framework removes SQL and row mapping, not all application policy.

For a different application that accepts the framework's schema and paging conventions, native `QuerydslDataFetcher` registration may require less adapter code. See [Spring GraphQL integration](https://docs.spring.io/spring-graphql/reference/data.html).

## Relationship fetching

The existing eager `Movie.director` association now declares EclipseLink `@JoinFetch(OUTER)`. ORM entity reads fetch movie and director in one SELECT, independent of response aliases or fragment placement. This avoids per-movie director queries and ensures detached entities have the relationship available during GraphQL completion.

The tradeoff is deliberate: ORM movie reads load director data even if the client omits it. GraphQL still returns only requested fields. This simple bounded to-one fetch plan fits this model; it is not a generic strategy for fetching arbitrarily large graphs. Adding collection relationships requires separate batching/fetch planning and pagination validation.

## Input binding and compatibility

Exact filters use Spring's Querydsl equality binding. The four range inputs (`yearFrom`, `yearTo`, `ratingMin`, `ratingMax`) configure generated numeric paths with `goe`/`loe`. Each input gets an independent binding set before predicates combine with AND. Reusing multiple aliases on the same path in one binding set can overwrite its binding, so the migration explicitly avoids that pattern.

The public schema and endpoints remain unchanged. Two edge behaviors are explicit:

- Empty string filters now return `FILTER_VALUE`. Spring's predicate builder treats empty input as absent, so rejecting it prevents accidental unfiltered queries.
- GraphQL cursor fingerprints now use canonical JSON containing a format marker, entity type, sorted filter keys, order and direction. Old JDBC cursors cannot continue on the new implementation. Start a new query after migration.

`first: 0` skips the entity SELECT. Selecting `totalCount` still executes and guards a count query. Normal paging still uses lookahead and preserves the original total budget, for example 75 results as 50 + 25.

## Java versions and build setup

| Module | Persistence namespace | Querydsl |
|---|---|---|
| Java 8 | `javax.persistence` | 5.0.0, JPA annotation processor |
| Java 17 | `jakarta.persistence` | 5.1.0 with Jakarta classifier |
| Java 21 | Same modern source tree | 5.1.0 with Jakarta classifier |

The Java 8 adapter uses Querydsl 5.0 because the 5.1 JPA artifact has a newer bytecode requirement. Both adapters implement the same connection contract. Annotation processors generate Q classes under each module's Maven target directory. Import/reload the changed Maven project in the IDE so its build classpath includes the new dependencies.

Run:

```bash
bash scripts/verify-matrix.sh
docker compose --profile variants up -d --build --wait
python3 scripts/smoke-matrix.py
```

The matrix script copies source into isolated build directories inside actual JDK containers. Host IDE background compilation cannot overwrite test classes. Reports are copied to `work/matrix/java8`, `java17`, and `java21` (ignored by Git). Existing recorded reports remain historical evidence; the current migration result is in [Querydsl verification](querydsl-verification.json).

New integration coverage exercises range/equality binding, aliased relationships with fragments/directives, a single ORM SELECT for multiple directors, optional counts, zero budgets, filter-order-independent cursors, changed-query rejection, and invalid/empty filter rejection. Existing tests continue to cover OData, paging budgets, SQL literal safety and plan enforcement.

For protocol selection and BFF tradeoffs, read [Choosing OData or GraphQL](choosing-odata-or-graphql.md). The presentation created before this migration describes the archived JDBC implementation.
